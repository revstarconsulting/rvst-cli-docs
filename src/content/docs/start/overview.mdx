description: A governed Kiro CLI setup — two repos, three agents, and four rules that keep autonomy safe.

**Kiro Workbench** is a governed setup on top of the [Kiro](https://kiro.dev)
CLI. It ships as **two repos**:

- **`rvst-cli`** — the Node CLI (`kiroctl`), its installers, and this
  documentation.
- **`rvst-registry`** — the content pack: agents, skills, gates, steering, the
  mission system, and memory.

`kiroctl` bootstraps the registry's content into Kiro's own config directory
(`$KIRO_HOME`), so every Kiro session — in any project — picks up the same
governed capability set.

## Four governing ideas

**Inert until armed.** Installing changes nothing by itself. Gates — the
enforcement layer — exist as scripts on disk but refuse nothing until you
create their flag file. A pack that starts blocking the moment it lands teaches
people to rip it out; this one earns trust one armed gate at a time.

**Opus orchestrates, Sonnet builds.** Three agents, three roles:

- **`dev`** — Opus-class. Plans, makes judgement calls, and drives the work.
  Stays in the main session.
- **`coder`** — Sonnet-class. Implements from a clear spec handed down by
  `dev`.
- **`scout`** — Sonnet-class, read-only. Cheap lookups — "where is X defined" —
  without touching the main session's budget.

Model routing is pinned explicitly in each agent's configuration. Never
Haiku-class, never `auto` — auto-routing can silently drop real work onto a
weaker model.

**Bolt-on, never subtract.** Updates add and extend; they don't silently remove
or rewrite something you've customized. Your edits survive an update.

**Evidence before done.** Claims of "fixed" or "done" need evidence, not
narrative confidence: root-cause the bug before patching it, prove a fix with a
red (failing) case that turns green, and pass QA's two-gate verdict — a change
must both **work** and **match the stated intent**.

## Capabilities

Everything the registry delivers falls into four kinds:

| Kind | What it is |
| --- | --- |
| **Agents** | The three roles above — who you talk to and who does the work. |
| **Skills** | On-demand protocols (QA, design, mission, architecture, review, and more) that load their full body only when a task matches. |
| **Gates** | Enforcement scripts that block a specific tool call once armed — e.g. a direct push to a protected branch. |
| **Steering** | Always-on context loaded on every turn — kept small and durable on purpose. |

See [Capabilities](/capabilities/overview/) for the full breakdown of each.
