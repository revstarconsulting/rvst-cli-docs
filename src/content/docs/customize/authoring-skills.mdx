## `skill-creator` is a skill, not an agent

Drafting a new skill goes through the **`skill-creator`** skill — invoked from
inside whatever agent session you're already in, not a separate dedicated
agent. Ask for it directly: "make a skill for X" or "create a skill for
reviewing migration files."

## Workflow

<Steps>

1. **Describe the skill.** Tell `skill-creator` what it should produce and
   when it should trigger — exact phrasing the user might say, or situations
   during a task that should invoke it.

2. **It drafts the `SKILL.md`.** Frontmatter (`name`, `description`) plus a
   scannable body — steps, output format, rules — matching the shape of the
   skills already installed in the project.

3. **It tells you where the file goes** — typically
   `.kiro/skills/<name>/SKILL.md`.

4. **Register it:**

   ```sh
   kiroctl onboard --kind skill --name <name> --source <path>
   ```

</Steps>

The same command onboards a custom **agent** or **hook** — just swap `--kind`:

```sh
kiroctl onboard --kind agent --name <name> --source <path>
kiroctl onboard --kind hook  --name <name> --source <path>
```

## Onboarding is governance-gated

`kiroctl onboard` checks the capability against house rules before it's
accepted, and refuses:

- a **Haiku-class model pin** on an agent — the standing rule is never
  Haiku-class for real work.
- an **auto-router** model setting — model routing has to be explicit, not
  `auto`.

## Onboarding is conflict-safe

Onboarding a capability that already exists at that name doesn't silently
clobber it — the same content-hash conflict handling used by `kiroctl sync`
applies here, so a collision surfaces as a **keep / overwrite / diff** choice
rather than an overwrite by default.

<Aside type="note">
`skill-creator` only authors and places the file. Registration — the part that
makes it a tracked capability — happens through `kiroctl onboard`.
</Aside>

## Rules of thumb

- **One skill, one job.** If the description covers two jobs, split it into
  two skills.
- **The trigger is the whole point.** A skill with a vague `description` never
  loads. Write it as "Use when the user asks X, says 'Y', or is doing Z."
- **Match the house style.** New skills should read like the ones already
  installed in the project.
