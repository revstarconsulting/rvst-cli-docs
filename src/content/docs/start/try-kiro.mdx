These are **replayed demo sessions** — a faithful mock of the Kiro chat window
using recorded prompts and responses. Click **Run demo** to watch a session play
out. Nothing runs live; it's here to show you the shape of a real session before
you try it yourself.

<Aside type="note">
Everything below runs under the **`dev`** agent (Opus). `dev` orchestrates:
it applies skills itself and delegates well-specified implementation to the
**`coder`** sub-agent (Sonnet) and read-only lookups to **`scout`** (Sonnet).
It never routes to a Haiku model or an auto-router.
</Aside>

## A mission, driven autonomously

The flagship workflow: hand `dev` a plan with the **`/goal`** loop and it sets a
**mission** (via the `mission` skill), enumerates every phase in an **acceptance
ledger**, then works phase-by-phase — delegating the build to the **`coder`**
sub-agent and lookups to **`scout`**, running the **`qa`** skill at the end of
each phase, and finally auditing the ledger requirement-by-requirement and
clearing. It only stops for a genuine one-way door; every reversible fork is
decided and logged.

## A feature, end to end

The full development lifecycle in one session: pull a user story from Azure
DevOps, have `dev` delegate the build to the **`coder`** sub-agent, review the
result, hand the backend work off, then file a protocol-compliant delivery task
back in ADO with the **`ado-write`** skill (title `<Role> - <Full Name> -
<MMDDYYYY>`, hour fields always `0`, `Custom.TeamCode`). Condensed from a **real**
session (User Story 136662).

## A pre-PR code review

The `review` skill reads for security and correctness first, orders findings by
severity, and explains *why* each one matters — then gives a clear verdict. (It
complements `qa`, which proves the rendered result in a real browser.)

<KiroSession session="review" />

## An architecture decision

The `architecture` skill states its assumptions, recommends **one** approach
(and says why), names the main alternative and when you'd switch to it, then
sketches the structure and flags the one-way-door decision.

<KiroSession session="architecture" />

## A cross-repo handoff

The `handoff` skill scans what the frontend actually built — API calls, types,
mocks — and produces a document the backend can implement from directly: the
exact endpoint, the data contract, and the assumptions made.

<KiroSession session="handoff" />

## A stakeholder breakdown

The `breakdown` skill turns a diff into a PM-friendly summary — plain-language
changes with file references, what was tested, and the risks — ready to paste
into a ticket.

<KiroSession session="breakdown" />

## Now try it yourself

Launch a client-bound session (see [Your first project](../first-run/)), switch
to the orchestrator, and give it a task:

```text
/agent dev
Pull context from ADO #<id> and implement it; delegate the build to coder,
then review it and run the qa skill.
```

For multi-phase work, set a mission and let the `/goal` loop drive it — see
[Missions & the /goal loop](../../workflows/missions/) for ready-to-use prompts.
