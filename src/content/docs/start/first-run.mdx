## Why you can't just run `kiro-cli`

A bare `kiro-cli` launch fails with:

```
profileArn is required
```

Kiro needs an AWS Identity Center (SSO) login before it can start a session,
and that login is scoped to a specific client. `kiroctl` supplies this by
launching through a **client-bound project** — a project directory tied to one
client's Identity Center configuration — rather than launching Kiro directly.

## Launch through a client-bound project

<Steps>

1. **Add the client.** This registers the client's Identity Center start URL
   and region:

   ```sh
   kiroctl client add --name "Acme" --idc-url https://acme.awsapps.com/start --region us-east-1
   ```

2. **Create the project**, bound to that client:

   ```sh
   kiroctl project new --dir ~/kiro/acme --client acme --scaffold
   ```

3. **Open it.** This performs the client's Identity Center login and launches
   the session:

   ```sh
   kiroctl open --dir ~/kiro/acme --run
   ```

   This logs you in via SSO, then launches `kiro-cli chat --agent dev` inside
   the project directory.

</Steps>

## The easier path

If you'd rather not drive this from a terminal, use the desktop **"Kiro - New
Project"** launcher, or run:

```sh
kiroctl gui
```

Both walk you through the same client-add / project-new / open sequence with a
graphical flow.

<Aside type="note">
Each client is one AWS Identity Center boundary with its own isolated
credential store. Switching clients never mixes credentials — a project bound
to one client cannot authenticate against another.
</Aside>

## Multi-repo projects

A project can span **several repos** — a frontend and a backend, say — so one
Kiro session and one mission work across all of them. A project is a workspace
folder bound to one client, plus a `.kiro/repos.json` mapping of its repos. Each
repo is either **cloned** from a git URL into a workspace subfolder, or **linked**
(symlinked) from a clone you already have.

From the GUI (`kiroctl gui`): when creating a project, add one or more repos —
each row is a **git URL** (cloned) or an **existing local path** (linked); the
project opens only once every repo is in place. Existing projects get an **Add
repo** box.

From the CLI:

```sh
kiroctl project add-repo --dir ~/kiro/acme --url git@github.com:org/frontend.git
kiroctl project add-repo --dir ~/kiro/acme --link /path/to/existing/backend
kiroctl project repos    --dir ~/kiro/acme
kiroctl open             --dir ~/kiro/acme --run   # clones any missing, then launches
```

<Aside type="note">
Cloning private repos uses your **existing git/GitHub credentials** (SSH or
`gh`) — the client governs AWS/Kiro SSO, not GitHub. A URL with an embedded
credential is rejected. `open` clones only what's missing and never auto-pulls,
so it won't disturb a working tree.
</Aside>
